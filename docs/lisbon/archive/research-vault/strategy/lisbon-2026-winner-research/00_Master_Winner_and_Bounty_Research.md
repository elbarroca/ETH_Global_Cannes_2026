## 4. Sponsor-by-sponsor winning precedent

### 4.1 1inch

Direct precedent: **Aqua Outcome Market** won the Buenos Aires Aqua track by making shared-liquidity capital efficiency the product, not a background integration. Other rewarded projects used Aqua for specific capital-reuse or flash-liquidity behavior.

What Lisbon requires:

- official Aqua or SwapVM contracts;
- a sophisticated DeFi position;
- observable token transfers in the final demo;
- event-window history and a working test/UI path.

Judge implication: an ordinary swap router or a logo-level Aqua reference will not compete. The custom position or SwapVM behavior must be the reason the product guarantee exists.

### 4.2 The Graph

Direct registered precedents include **Agentica**, **RangeSeeker**, and **ALA**. These projects used live indexed data to drive a decision, simulation, or strategy rather than merely draw a dashboard.

Lisbon publishes three distinct lanes:

1. **AI Tooling** — reusable MCP, SKILL, plugin, configuration, payment, or infrastructure. Usefulness and reusability dominate the scoring.
2. **AI Use Case** — live Graph data must be load-bearing to an AI decision or action. Graph use has the highest weight.
3. **Composable/Standardized Products** — compose at least two Graph products or make meaningful use of a standard schema. One ordinary query is insufficient.

Judge implication: live data, named endpoints, clear install/use documentation, and an obvious post-hackathon consumer beat a one-off wrapper.

### 4.3 World

Precedents such as **DIVE**, **VEIL VPN**, and **Proof-of-Human** made uniqueness control a scarce right: committee membership, access, or one-person participation.

Lisbon state: `PENDING`. Do not assume AgentKit, MiniKit, World ID, ProveKit, payout, or evidence terms from older events. World should not be selected until the official track makes human proof control an actual quota, approval, or replay invariant.

### 4.4 Hedera

Precedents reward public, inspectable state: payments, consensus records, token lifecycle, scheduling, or agent identity. **DIVE** and **Azimuth** are registered examples of sponsor state being visible in the product proof rather than hidden as infrastructure.

Lisbon lanes are Agentic Payments, Tokenization, No Solidity Allowed, and Cross-Chain Automation. The last lane is technically expensive: Schedule Service must trigger Axelar GMP and a real destination-chain effect without a project bot, keeper, or cron.

Judge implication: show the Testnet transaction or service identifier, then show Mirror/Hashscan readback and a replay that creates no duplicate effect.

### 4.5 0G

Open Agents winners split cleanly between reusable frameworks and autonomous products. **ACL**, **Mendel**, **Immunity**, **Brainpedia**, and **CodeGuardian iNFT** made storage, compute, TEE evaluation, provenance, or iNFT lineage part of an inspectable claim. Cannes winner **Shawarma Orchestrate** is a relevant DeFi/product precedent.

Lisbon preserves the same product-versus-tooling distinction and adds an explicit Continuity lane. A new end-user product should not claim tooling merely because it has internal utilities, and Project B cannot claim Keep Building. Every applicable 0G submission also needs team names, Telegram and X contacts, public source, addresses, a live-demo link, an under-three-minute video, the used SDK/features, and any required Agentic ID explorer link.

Judge implication: show a real 0G request, proof/identifier, readback, and a fail-closed response to missing or tampered evidence.

### 4.6 Uniswap Foundation

**Zuno**, **Moai**, **Alps**, **CrossLiquid**, **PrivBatch**, **Eidolon**, **GrimSwap**, and **Better Wallet** show the field's maturity. LP rebalancing, trading swarms, privacy/MEV hooks, intent execution, and wallet safety have dense recent precedent.

Lisbon API Integration requires a valid Developer Platform API key, a core route/execution/liquidity/coordination use, public source, exact code pointers, `FEEDBACK.md`, and the feedback form. Stack Contribution is Continuity and therefore unavailable to new Project B.

Judge implication: the API must own a necessary economic effect. A quote-only integration, manual fallback, placeholder address, or unreplayed critical route is not enough.

### 4.7 Sui

**OverFlow**, **Pay402**, **Zebra**, **Reputa**, and other HackMoney notable projects show that native object models, Move, PTBs, Seal, Walrus, DeepBook, or zkLogin must visibly change the workflow.

Lisbon has one new-app lane and one existing-app integration/port lane. New Project B can only pursue the former.

Judge implication: demonstrate an object/blob/transaction identifier and a native failure such as revoked decryption, invalid PTB rejection, or policy denial.

### 4.8 ENS

**ACL**, **Brainpedia**, **Skillname**, **ENSign**, **Reckon402**, **AgentIndex**, and **VEIL VPN** give directories, agent discovery, capabilities, and naming dense recent precedent.

Lisbon offers Creative Use, AI Agent Integration, and Continuity Integration. Functional, non-hard-coded ENS behavior, a demo/video, and a Sunday-morning booth presentation are required.

Judge implication: resolution must change who or what the system trusts, discovers, or permits. A human-readable label alone is cosmetic.

## 5. What winners have in common

The following are evidence-backed synthesis, not published universal judging rules unless a partner rubric says so.

### 5.1 One legible user loss

The strongest projects make the failure understandable in one sentence: duplicate access, unsafe rebalance, stale data, leaked bid, unverifiable payment, or ambiguous agent authority. Protocol-first narratives make judges work too hard.

### 5.2 Sponsor causality

Use the removal test:

> If removing the sponsor SDK or protocol leaves the user guarantee unchanged, the integration is cosmetic.

Each selected sponsor should own a different invariant: live evidence, private/verifiable reasoning, identity/authority, economic state, or recovery.

### 5.3 One complete loop

The highest-signal demos travel from an input through decision, policy, approval, real state change, public readback, and canonical receipt. Three half-working integrations are weaker than one replayable loop.

### 5.4 Model proposes; deterministic policy authorizes

Models are valuable for semantic interpretation, classification, query construction, or proposal generation. They should not receive keys or create arbitrary calldata. Caps, allowlists, deadlines, replay protection, validation, and isolated signing remain deterministic.

### 5.5 A negative path is visible

A tampered proof, stale endpoint, revoked permission, unsafe instruction, duplicate request, or missing delivery should produce an explicit refusal. This turns “trust us” into an observable safety property.

### 5.6 Exact public evidence

Winning evidence is inspectable: transaction hash, object ID, schedule ID, HCS sequence, Graph query/endpoint/block, 0G proof, deployment address, content hash, or deterministic failure record.

### 5.7 Reusability and continuation

For tooling tracks, judges explicitly reward an installable CLI/MCP/SKILL/SDK, clear README, example, test fixture, and obvious user beyond the event. For apps, a credible narrow wedge beats a generic platform roadmap.

## 7. Bounty integration rules

### 7.1 Portfolio shape

- Select no more than three partners; prefer two load-bearing partners.
- Give each partner a separate causal role.
- Maintain one independent fallback that does not share the primary dependency.
- Add a third sponsor only after the core loop and negative path are green.
- Do not optimize for announced pool size. Prize amount has zero weight in the build score.
- Cap planning value at one highest slot per partner. Expected winnings remain `NOT ESTIMABLE`; budget value remains `$0`.

### 7.2 Sponsor compatibility map

## 9. Score rubric

| Criterion | Weight | Green evidence |
|---|---:|---|
| User loss and agent necessity | 15 | The failure and why semantic reasoning is needed are clear |
| Sponsor causality | 20 | Removing a sponsor breaks a named guarantee |
| Replayability, reconciliation, receipt | 20 | Restart/replay produces no ambiguous or duplicate effect |
| Event-window feasibility and access | 20 | Credentials, Testnet, docs, and recovery path work early |
| Four-minute legibility | 10 | One visible input-to-receipt story |
| Novelty against precedent | 10 | Materially differs from documented winners |
| Adoption wedge | 5 | A specific next user, install path, or workflow exists |

The deterministic total is:

`score_100 = user_loss_agent_15 + sponsor_causality_20 + replay_receipt_20 + feasibility_access_20 + demo_legibility_10 + novelty_10 + adoption_wedge_5`

Ranking order is total descending, then feasibility/access descending, then fewer selected partners, then concept name alphabetically. The CSV records every component and its evidence basis; prize amount is excluded from the score.

Fatal gates override the score:

- invalid H0 provenance or pre-existing design reuse;
- ineligible or unpublished track;
- cosmetic sponsor integration;
- model-held keys or arbitrary model-generated calldata;
- no real sponsor-native state change;
- success-shaped mocks or placeholder evidence;
- duplicate or ambiguous economic effect;
- no refusal, failure, or replay path.

## 10. Four-minute judge sequence

This is a generic live-demo or judging-rehearsal pattern, not a product design. It is not a universal upload duration: compress a shared Graph/0G partner video to 2:00–2:59.

| Time | Proof |
|---:|---|
| 0:00–0:35 | State one user loss and show the unsafe or ambiguous input |
| 0:35–1:20 | Show the agent's bounded proposal and the deterministic authority boundary |
| 1:20–1:55 | Tamper, revoke, stale, duplicate, or exceed a cap; show explicit refusal |
| 1:55–2:50 | Run the valid path with any required human approval |
| 2:50–3:25 | Show sponsor-native state change and independent/public readback |
| 3:25–3:50 | Replay or restart; show no duplicate effect and the canonical receipt |
| 3:50–4:00 | Name the exact partner tracks and public evidence identifiers |

## 11. H0 selection and stop contract

### Before H0

- Keep all outputs as research only.
- Recheck the event guide, rules, prize index, every candidate partner page, access, and World.
- Seek a written organizer ruling if any pre-H0 project-specific planning might be reused.
- Do not create Project B repository history, prompts, specs, designs, assets, transactions, or deployment state.

### After captured H0

1. Start a clean repository and provenance log.
2. Independently identify the user loss and product design without copying pre-H0 named concepts or flows.
3. Run small real-access probes for the selected sponsor-native path.
4. Select one primary loop and one independent fallback by an explicit early gate.
5. Build the success path, refusal path, reconciliation/replay path, and evidence receipt in that order.
6. Add a second sponsor only when its removal demonstrably breaks a product invariant.
7. Add a third sponsor only after the core path is green and time remains.

### Decision states

- `BUILD` only after H0 provenance, eligibility, access, native state, refusal, replay, and receipt gates are green.
- `NARROW` while more than one core dependency or sponsor role is unresolved.
- `STOP` if the build needs static/mock core data, placeholder proofs, model authority over signing, unreplayable cross-chain behavior, or a cosmetic sponsor.
